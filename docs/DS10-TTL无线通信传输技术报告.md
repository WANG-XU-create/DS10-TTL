## 摘要

DS10-TTL 是一款星闪（SLE）无线透明串口桥：一端串口写入的字节经无线送达对端、原样吐出，
设备本身不理解上层协议（Modbus 模式下仅读首字节站号做路由）。本项目在其上构建了一套
ROS 2 通信栈（三个软件包），实现并实测验证了两条通信能力：

1. **主从并行双向通信** —— 1 主对多从、下行按站号点对点、上行按站号识别来源，且下行与
   上行可**同时并发进行而互不干扰**（实用负载内零冲突）。
2. **主从转发通信** —— 主机向从机1 发请求，从机1 按**数据内容自主决定**回复该转发给谁，
   主机据此把回复转发给第三方从机，构成三跳链路；端到端实测 **~67 ms**。

关键实测结论：透传对数据字节/CRC 完全透明；单向延迟随帧长非线性暴涨（32 B ~14 ms，
1400 B ~419 ms 且成功率仅 44%）；上行存在 ~1100 B 帧长天花板而下行可达 ~4095 B（链路
不对称）；主机连续下行需 ≥5 ms 帧间隔。这些约束共同界定了系统的可靠工作区。

**报告导读**：第一部分设备性能参数；第二部分硬件部署与设备（上位机）配置；第三部分本项目
设计的 ROS 通信软件包（作用与用法）；第四、五部分分别是并行双向、转发两条通信的技术路线；
第六部分结论与部署建议。

## 第一部分　设备性能参数

### 1.1 物理与接口参数

| 类别 | 参数 | 值 |
|------|------|-----|
| 无线制式 | 星闪 SLE | GFSK / Polar 码可选 |
| 频段 | 2400–2483.5 MHz | 1 MHz 步进 📄 |
| 发射功率 | 可配 | 0 / 3 / 6 / 9 / 10 dBm 📄 |
| 传输距离 | 空旷典型 | 200 m 📄（障碍环境缩短） |
| 拓扑 | 一主多从 | 1 主 ≤ **15** 从 📄 |
| 串口电平 | TTL | 8N1 等可配 |
| 串口波特率上限 | DS10-TTL | 4 Mbps 📄（本项目用 115200 ✅） |
| 工作模式 | 三选一 | 广播 / **Modbus** / 规则路由 |
| 功耗 | 5 V 供电 | 休眠 <10 μA，接收 ~20 mA，发射 10 dBm ~40 mA 📄 |

✅ **本项目实测配置**：DS10-TTL，115200 8N1，Modbus 模式，SLE 功率 0x07，GFSK 高功率档，
可靠广播，近距离桌面（<2 m）稳定工作。

### 1.2 透传保真性 ✅

DS10 对串口字节流**透明透传**：不改动数据内容、功能码与 CRC。本项目通过对比发送端与接收
端字节逐一验证，随机填充的 Modbus 0x10 帧被从机原样接收，站号/功能码/CRC 全部不变。这是
上层能自定义任意帧格式（含本项目的事务头）的前提。

### 1.3 端到端延迟 ✅（关键实测）

官方文档未给延迟指标。本项目用主/从 DS10 同挂一台 Jetson、共用时钟测量单向延迟
（各尺寸 50 次）：

| 载荷 | 整帧 | 单向延迟（含从机串口接收） | 纯无线估计 | 成功率 |
|------|------|---------------------------|-----------|--------|
| 32 B | 43 B | **13.7 ms**（12–15，抖动极小） | ~10 ms | 50/50 |
| 240 B | 251 B | **73.7 ms**（72–77） | ~52 ms | 50/50 |
| 1400 B | 1411 B | **419 ms**（413–422） | ~297 ms | **22/50 (44%)** |

**关键结论：**

1. **延迟随帧长非线性暴涨**：载荷放大 44 倍、延迟放大约 30 倍。根源是 DS10 可靠广播的
   **分片 + 逐片确认**——帧越大分片越多，确认往返累加。
2. **大帧（1400 B）不仅慢、还不可靠**：成功率仅 44%，推测大帧任一分片未确认即整帧丢。
3. **单向 ≪ 往返**：大帧往返（去 + 回各一次分片确认叠加）会放大到约 2 秒、几乎全超时；
   单向才是业务真实场景（下发/上报）的准确值。

### 1.4 帧长上限与方向不对称 ⚠️（关键实测）

| 方向 | 实测可达单帧 | 说明 |
|------|-------------|------|
| 下行 主机 → 从机 | **~4095 B**（整帧） | 分片重组工作，实测 2013 B 完整到达，超文档 1500 B；4109 B 被截断成 4095 B（疑 off-by-one） |
| 上行 从机 → 主机 | **~1100 B** | 实测 1008 B OK、**1108 B 起 100% 失败**（边界很陡） |

⚠️ **链路上下行不对称**：上行天花板（~1100 B）远低于下行（~4095 B）。已用「从机主动上行、
完全绕开应用层」独立复现，故属**电台/配置层面的限制**，非驱动缺陷；`resync_dropped_bytes`
恒为 0 说明是整帧无线丢失而非字节损坏。此上限与文档「1501–4096 B 自动分包重组」不一致，
疑与当前 SLE 档位/上行调度有关，**换配置或固件后需复测**。

**业务层限制**：驱动限整帧 ≤ 4095 B（data ≤ 约 4080 B），TX 超限拒绝并计
`tx_rejected`，不做跨帧重组。

### 1.5 链路可靠性与噪声地板 ✅

- **到达率**：实用负载（≤ 240 B）下近距离桌面链路接近 100%，偶发单帧丢失属无线本征抖动。
- **重同步丢字节** `resync_dropped_bytes`：混合定界法在链路干净时实测 **= 0**，是链路噪声
  地板的量化指标。
- **可靠性归属**：无线链路非 100% 可靠，严格不丢由应用层用 `tx_seq`/`rx_seq` 对账重传。

### 1.6 性能参数速查

| 指标 | 值 | 来源 |
|------|-----|------|
| 单向延迟 @32 B | 13.7 ms | ✅ §1.3 |
| 单向延迟 @240 B | 73.7 ms | ✅ §1.3 |
| 下行单帧上限 | ~4095 B | ✅ §1.4 |
| 上行单帧上限 | ~1100 B | ✅ §1.4 |
| 主机连续下行最小帧间隔 | 5 ms（建议 10 ms） | ✅ §4.8 |
| 安全发送间隔 | ≥ 单帧串口传输时间 × 3~5 | ✅ §4.6 |
| 重同步丢字节（干净链路） | 0 | ✅ §1.5 |
| 三跳转发端到端 @60 B | ~67 ms | ✅ §5.8 |

## 第二部分　硬件部署与设备配置

### 2.1 硬件连接拓扑

每台 DS10-TTL 通过 **USB-TTL 转换器**接到一台 Jetson 的 USB 口，DS10 之间靠星闪无线相连：

```
调试阶段（主从同挂一台 Jetson, 便于共用时钟测延迟/并发）:
   Jetson ─USB┬─ CH340 ─ DS10 主机  ──┐
              ├─ CH340 ─ DS10 从机1  ─┤ 星闪 SLE 无线
              └─ CH340 ─ DS10 从机2  ─┘

部署阶段（生产, 每台 Jetson 只接一台 DS10）:
   Jetson_主 ─USB─ CH340 ─ DS10 主机  ┐
   Jetson_从1─USB─ CH340 ─ DS10 从机1 ┤ 星闪 SLE 无线（不同机器, 只靠电台相连）
   Jetson_从2─USB─ CH340 ─ DS10 从机2 ┘
```

- **调试阶段**：主机 + N 从机同挂一块 Jetson（多个 `/dev/ttyUSB*`），方便用同一时钟测量
  延迟与双向并发（第一、四、五部分的大量实测即在此形态下完成）。
- **部署阶段**：主机与各从机分处不同 Jetson，通过无线电台通信；每台 Jetson 只接一台 DS10。

### 2.2 /dev/ttyUSB* 节点映射 ⚠️

✅ **实测环境**：USB-TTL 转换芯片为 **CH340（USB ID `1a86:7523`）**，三台设备型号完全相同。

**关键问题——`/dev/serial/by-id/` 撞车**：CH340 未烧唯一序列号，三台设备在 by-id 下**名字
完全相同**（均为 `usb-1a86_USB_Serial-if00-port0`），无法区分。因此：

| 阶段 | 区分手段 | 说明 |
|------|---------|------|
| 调试（主从同机） | **物理口 by-path** | 如 `/dev/serial/by-path/platform-3610000.usb-usb-0:2.1:1.0-port0`；三口对应 USB 树的 2.1 / 2.2 / 2.3 |
| 部署（单机单设备） | **by-id** | 唯一设备，撞车无所谓，回归 by-id 即可 |

⚠️ **`ttyUSBx` 编号不稳定**：`ttyUSB0/1/2` 会在重启/重插时对调，**不要把「ttyUSB0=主机」
当稳定事实**。本项目 `start_ds10.sh` 默认按 `ttyUSB0=主机、ttyUSB1=从机1、ttyUSB2=从机2`
约定启动，但这只是当前枚举顺序下的约定；换机或重插后需用 `MASTER_PORT=... ./start_ds10.sh`
或 by-path 显式指定。

> 根因：CH340 无序列号是硬件限制，软件无法绕过；要 by-id 天然区分只能换带唯一序列号的芯片
> （FTDI FT232 / 可烧号的 CP2102）。物理口映射仅为调试期临时手段，不做永久 udev 配置。

**权限**：串口设备属 `dialout` 组，运行用户需加入该组
（`sudo usermod -a -G dialout $USER` 后重新登录）。

### 2.3 DS10 设备配置（官方上位机操作）

> **本节所有操作在官方《DS10 星闪 DTU 配置小程序使用说明书》中有逐步图文指导**（微信小程序，
> 蓝牙连接）。本报告只提炼与本项目相关的关键绑定关系，不复述每一步；具体界面与步骤请以
> 官方说明书为准，对应章节号见下表。AT 命令方式另见官方《DS10-AT 指令集》。

DS10 出厂需先用配置小程序设定角色、通道与参数，才能投入使用。核心流程：

| 步骤 | 操作要点 | 官方说明书章节 |
|------|---------|--------------|
| ① 选择角色 | 每台设备选**主模式**或**从模式**：主机才有通道管理，从机只设自身硬件参数 | §01 · 1.4 |
| ② 连接设备 | 蓝牙选中目标设备（核对 SN）、读取当前配置 | §02 |
| ③ 主机选工作模式 | 主机选 **MODBUS 模式**（本项目用；另有广播 / 规则路由） | §03 · 3.1 |
| ④ 主机添加从机 | 通道管理里开启通道，每通道绑定一台从机（扫码 / 输入 SN） | §04 · 4.1 |
| ⑤ 主机绑定 Modbus 站号 | Modbus 模式下建立**「通道 ↔ Modbus ID」**绑定，站号 1–247 | §04 · 4.2 ② |
| ⑥ 从机设硬件参数 | 从机只需设串口（8N1）与发射功率，无需通道/站号 | §05 |
| ⑦ 保存并切 RUN | 保存 → 重读核对 → 把模块 **RUN/DEBUG 开关拨到 RUN** | §06 · 6.3 |

**Modbus 模式的路由机制**（本项目通信的基石，官方说明书 §04·4.2②）：
- 主机把**通道**与 **Modbus 站号（ID）**绑定。例：通道 1 ↔ 站号 1，通道 2 ↔ 站号 2。
- 下行：主机收到首字节站号=N 的帧 → 路由到绑定站号 N 的通道 → 对应从机。
- 上行：从机发出的帧首字节带自身站号 → 主机据此识别来源。
- 一个通道可绑多个站号，同一站号也可绑到不同通道（跨通道重复不算冲突）。

✅ **本项目实测绑定**：通道 1 ↔ 站号 1、通道 2 ↔ 站号 2；主机正确按站号区分来源（2 从并发
验证通过，见 §4.7）。**两端串口参数（波特率/数据位/校验/停止位）必须一致**，否则无法收发。

**从机设置为从机**（官方说明书 §01·1.4 + §05）：进入配置页时对该设备选**从模式**，之后
只出现「硬件配置」（串口、SLE 发射功率），不出现主机配置与通道管理——即从机无需知道站号
绑定，站号路由完全由主机侧的通道绑定决定。

⚠️ **投入使用前务必把 RUN/DEBUG 开关拨到 RUN**（官方 §06·6.3）；停在 DEBUG 侧设备不进入
正常透传工作态。

## 第三部分　ROS 通信软件包（本项目设计）

本项目在 `/home/nvidia/DS10_Modbus/`（独立 colcon 工作区）下设计了**三个 ROS 2 软件包**，
把「串口 + 组帧 + CRC + 帧定界 + 站号寻址 + 转发编排」全部封装，业务节点只需收发消息。

### 3.1 软件包一览

| 包 | 类型 | 作用 |
|----|------|------|
| `ds10_interfaces` | 消息接口（IDL） | 定义 `Frame.msg`——承载一条透传消息（站号 + 功能码 + 数据 + 对账序号），主/从/中继共用 |
| `ds10_driver` | C++ 驱动 | 串口 ↔ 话题桥：把 `Frame` 组成 Modbus RTU 帧写串口，把串口字节流解成 `Frame` 发布；含组帧/CRC/混合定界/断线重连/诊断。`role` 分主/从 |
| `ds10_relay` | C++ 应用 | 三跳请求-应答-转发：`role` 分 relay（主机侧编排）/ responder（从机侧应答、按内容选转发目标） |

依赖关系：`ds10_driver`、`ds10_relay` 均依赖 `ds10_interfaces`；`ds10_relay` 建在
`ds10_driver` 的话题之上，不直接碰串口。

### 3.2 `ds10_interfaces` —— 消息契约

`Frame.msg` 字段：`station_id`（Modbus 站号）、`function_code`（Modbus 功能码，透传不解析）、
`data`（数据字段字节）、`tx_seq`/`rx_seq`（端到端对账序号，应用层可选用）。业务层只面对这
三个业务字段，无需关心串口与组帧。

### 3.3 `ds10_driver` —— 收发驱动

打开一个串口，桥接两个话题：

| 话题 | 类型 | 方向 | 说明 |
|------|------|------|------|
| `~/tx` | `Frame` | 应用 → 驱动 | 组 Modbus RTU 帧写串口 |
| `~/rx` | `Frame` | 驱动 → 应用 | 解出完整帧后发布 |
| `/diagnostics` | `DiagnosticArray` | 驱动 → 应用 | 连接状态、收发帧计数、`tx_rejected`、`resync_dropped_bytes` |

`role=master`：`~/tx` 的 `station_id` 作目标从机号、`~/rx` 填来源从机号；
`role=slave`：`~/tx` 用参数 `station_id` 覆盖、`~/rx` 只发本机站号的帧。技术细节见第四部分。

**参数**：`port`、`baud`、`role`、`station_id`（从机必填 1–247）、`frame_timeout_ms`
（定界静默阈值，默认 20）、`max_frame_bytes`（默认 4095）、`tx_topic`/`rx_topic`（可重映射，
支持一机多实例）。

### 3.4 `ds10_relay` —— 三跳转发

同一可执行 `relay_node`，`role` 分两端：
- `role=relay`（主机侧）：发请求给从机1 → 按事务号匹配回复 → 读回复里的 `dst` → 转发给
  `dst` 指定的从机。参数 `slave1_id`、`timeout_ms`（默认 1500）、`max_retries`（默认 2）。
- `role=responder`（从机侧）：收到请求 → 用 `route_map`（`"关键字:站号,..."`）按载荷内容
  选 `dst` → 回复。参数 `route_map`、`default_dst`（默认 0=不转发）。

话题：`~/trigger`（`std_msgs/String`，外部触发一次事务）、`~/stats`（计数快照）。
技术细节见第五部分。

### 3.5 编译与运行

```bash
cd ~/DS10_Modbus
colcon build                                   # 首次或改代码后
source install/setup.bash

# —— 基础收发：只起 3 个驱动（一主两从）——
./start_ds10.sh                                # 主=ttyUSB0 从1=ttyUSB1 从2=ttyUSB2

# 业务层直接收发（举例：主机发给从机1）
ros2 topic pub --once /master/tx ds10_interfaces/Frame "{station_id: 1, function_code: 16, data: [1,2,3]}"
ros2 topic echo /slave1/rx                     # 从机1 收到

# —— 三跳转发：全自动栈（驱动+应答器+中继）——
./start_relay.sh                               # 一键
ros2 topic pub --once /ds10_relay/trigger std_msgs/String "{data: 'temp=25.3'}"
ros2 topic echo /ds10_relay/stats

# —— 转发的手动/耗时测试：只起驱动, 见各脚本 —— 
python3 test/ds10_relay_master.py --timeout 60 --retries 0      # 手动敲请求
python3 test/ds10_relay_responder_interactive.py --default-dst 2 # 手动打回复
python3 test/ds10_relay_timing.py --count 20                    # 端到端耗时
```

也可用 launch 文件逐节点起（便于调参）：`ros2 launch ds10_driver ds10_master.launch.py`、
`ds10_slave.launch.py`、`ros2 launch ds10_relay ds10_responder.launch.py route_map:="temp:2"`、
`ds10_relay.launch.py`。各包 `README.md` 有完整话题/参数表与快速开始。

⚠️ **自动栈与手动/耗时测试不能同跑**：都跑会一个请求两份回复（应答器抢答），脚本会检测并
告警。基础/手动测试用 `start_ds10.sh`（仅驱动），全自动演示用 `start_relay.sh`。

## 第四部分　主从并行双向通信技术路线

### 4.1 需求

1 主机对最多 15 台从机；下行需点对点寻址、上行需识别来源；且下行（主机发指令）与上行
（从机报数据）应能**同时并发**而互不干扰。设备本身只透传字节，寻址与并发的可靠性需由
上层技术路线保证。

### 4.2 技术路线总览

```
   业务节点                ROS 2 驱动 (ds10_driver)              DS10 无线
 ┌──────────┐   ~/tx   ┌───────────────────────────┐  串口   ┌────────┐
 │ 发布 Frame├────────►│ 组 Modbus RTU 帧 + CRC     ├────────►│  SLE   │
 │(站号+数据)│         │ (tx 回调, 写锁保护)        │         │ 无线层 │
 │          │  ~/rx   │ reader 线程: 读串口         │◄────────┤ 站号   │
 │ 订阅 Frame│◄────────┤ 混合定界法解帧 + CRC 校验  │  串口   │ 路由   │
 └──────────┘         └───────────────────────────┘         └────────┘
```

核心思想：把「串口 + 组帧 + CRC + 帧定界 + 站号寻址」全部下沉到驱动，业务层只面对
`station_id / function_code / data` 三个字段。同一份驱动用 `role` 参数区分主/从。

### 4.3 链路帧格式：标准 Modbus RTU

利用 DS10 的 **Modbus 模式**——设备读数据**首字节（站号 1–247）**做路由（配置见 §2.3）。
链路帧直接用标准 Modbus RTU：

```
[站号 1B][功能码 1B][数据 N B][CRC-16/MODBUS 2B 小端]
```

- CRC 固定 **CRC-16/MODBUS**（poly 0xA001 反射、init 0xFFFF），覆盖站号+功能码+数据。
- **不叠加应用层长度前缀帧**：站号即寻址、Modbus CRC 即校验，再套一层是冗余且会破坏
  DS10 的站号路由（早期 0xAA55 魔数方案已否决）。
- **站号语义随角色/方向变化**：主机 TX 填目标从机号、RX 填来源从机号；从机 TX 由驱动用
  参数站号覆盖、RX 只发本机站号的帧。这套约定使主机端**单串口即可对 15 台从机区分收发**。

### 4.4 混合定界法（并发可靠性的关键）

Modbus RTU 帧无长度字段，而 DS10 无线链路会**粘包/拆包**（多帧粘连或单帧拆分），故单凭
静默间隔无法可靠切帧。驱动 reader 线程采用**混合定界法**：

1. **静默间隔粗切突发**：`frame_timeout_ms`（默认 20 ms）判定一段突发结束。
2. **CRC 试探细切帧**：从每个候选起点要求站号 ∈ [1,247]，递增候选长度试 CRC，命中即认定
   一帧；配不出的字节逐字节滑过重同步，尾部半帧保留待下次拼接。CRC 失败的字节段不产出
   `Frame`（计入 `resync_dropped_bytes`）。

✅ 实测 100% 到达率、`resync_dropped_bytes = 0`。这套定界法是并发场景可靠的基础——多从
上行帧粘连时，靠 CRC 试探仍能逐帧正确切分。

### 4.5 线程模型（并发的实现基础）

- **专用 reader 线程**：循环阻塞读串口 → 解帧 → 发布 `~/rx`。串口读是阻塞的，独立成线程
  避免占用 executor。
- **tx 回调**：在订阅回调里组帧写串口。
- **写锁**：读写共用一个串口 fd，用互斥锁保护并发访问。
- **MultiThreadedExecutor**：tx 回调与诊断在负载下保持响应。
- **自动重连**：reader 检测到串口错误即关闭→退避→重开，期间诊断报 disconnected。

这套模型使**同一驱动实例可同时收（reader 线程）和发（tx 回调）**，是主机侧下行+上行并发
的软件基础。

### 4.6 实测：主从双向并发零冲突 ✅

官方文档未说明无线链路是半双工还是全双工。本项目用「主机→从机1 下行」与「从机2→主机
上行」**同时进行**，三阶段基线对照（先各测单向基线，再用 `threading.Barrier` 同一瞬间放行
测并发）：

| 负载 | 发送间隔 | 下行 基线→并发 | 上行 基线→并发 | 判读 |
|------|---------|--------------|--------------|------|
| 32 B | 50 ms（宽裕） | 100% → 100% | 100% → 100% | ✅ 无冲突 |
| 240 B | 100 ms（宽裕） | 100% → 100% | 100% → 100% | ✅ 无冲突 |
| 240 B | 10 ms（超发） | 45.5% → 0% | 91% → 0.5% | ❌ 坍缩（见下） |

**结论：**

1. **实用负载内双向并发零冲突**：只要发送速率在链路吞吐内，主机下行与从机上行同时进行、
   两向均 100% 到达。**这回答了核心问题——主从双向通信在正常负载下不冲突。**
2. **坍缩仅在过载区**：240 B/10 ms 时发送间隔已小于单帧串口传输时间（~22 ms），属严重
   超发，此时单向基线本身就已崩溃，无法干净归因于「半双工争用」。故诚实标注：**DS10 无线
   是否半双工、纯冲突量多大，尚未被干净分离**（需基线健康前提下持续加压才能测得）。

**安全发送间隔经验规则**：
> 发送间隔 ≥ 单帧串口传输时间 × 3~5；单帧串口传输 ≈ 整帧字节数 × 10 / 波特率（8N1）。
> 例：240 B 整帧 ~251 B → ~22 ms → 安全间隔 ≥ 80~100 ms。

### 4.7 实测：多从并发上行为「帧依次调度」 ✅

2 台从机屏障同步一键并发上行，主机按站号对账：

| 测试 | 站号1 到达率 | 站号2 到达率 | 意外站号/乱序 |
|------|-------------|-------------|--------------|
| 50 ms 间隔 / 各 200 帧 | 99.5% | 100% | 无 |
| 20 ms 间隔 / 各 ~313 帧 | 100% | 100% | 无 |

**DS10 多从并发上行是「帧依次调度」而非「字节交织」**：若字节交织，CRC 试探会大面积配不
出、到达率明显下降甚至偶发假帧；实际两站号几乎全达、站号干净区分，证明 DS10 固件在无线层
把各从机的帧排队依次送达。**1 主 15 从的来源识别机制成立**（2 从证明机制，更多从为同一
机制扩展）。

### 4.8 关键约束：主机连续下行需帧间隔 ⚠️

✅ 实测：主机背靠背（间隔 <1 ms）向从机1、从机2 连发两帧，从机1 稳定收到、**从机2 每次
必丢**（10 次循环 10 次全丢，零随机性）。丢失点在 **DS10 设备内部**（驱动 `tx_frames` 计满、
`resync_dropped_bytes=0`，字节已完整交给设备串口），是固件处理第一帧（组包、切通道、发射）
期间丢弃了紧随的第二帧。

| 两帧间隔 | 从机1 | 从机2 |
|----------|-------|-------|
| 0 ms | 到达 | **丢失** |
| ≥ 5 ms | 到达 | 到达 |

**对策**：主机连续下行帧间隔 **≥ 5 ms**（驱动脚本默认 10 ms 留一倍余量，实测 80/80 零丢失）。
轮询 15 从一圈按此估 ≈ 150 ms。**该约束仅限同一主机连续下行**；上行并发（§4.7）与双向
交叉（§4.6）不受影响。

### 4.9 小结

主从并行双向通信的技术路线 = **Modbus 站号路由（设备层）+ 标准 Modbus RTU 帧 + CRC-16/
MODBUS 校验 + 混合定界法（软件层）+ reader 线程/tx 回调/写锁的并发模型**。实测在实用负载
内下行、上行、双向并发均可靠；边界是「主机连续下行需 ≥5 ms 间隔」「上行 ~1100 B 帧长天花板」
「过载区坍缩」。

## 第五部分　主从转发通信技术路线

### 5.1 需求

主机向从机1 发数据 → 从机1 收到后回复 → 主机把回复转发给从机2，构成三跳链路。且转发目标
**不应由主机写死，而应由从机按数据内容自主决定**——从机想把不同数据派往不同目标（如温度
数据转给站2、湿度转给站3），或拒绝转发，都由从机说了算。新增目标不需改主机配置。

### 5.2 技术路线总览

在 `ds10_driver` 话题之上新增 `ds10_relay` 包，同一可执行文件用 `role` 分两端：

```
        ┌──────────── relay (主机侧) ────────────┐
[1] 请求 │ /master/tx  station=从机1              │
        │ F1 F1 <txn> <请求载荷>                 │
        └────────────────┬───────────────────────┘
                         ▼ 下行无线
        ┌────────── responder (从机1 侧) ─────────┐
[2] 应答 │ 按 route_map 匹配载荷内容 → 选出 dst    │
        │ /slave1/tx: F1 F2 <txn> <dst> <回复载荷>│
        └────────────────┬───────────────────────┘
                         ▼ 上行无线
[3] 转发 │ /master/rx (来源=从机1, txn 匹配) → 读 dst
        │ → /master/tx station=dst → 目标从机 (下行无线)
        │ dst=0 则不转发
```

**核心设计：路由权在从机，不在主机。** 转发目标是从机在回复里携带的 `dst` 字节；主机只做
合法性校验（`dst ∈ [1,247]` 且 ≠ 来源站号），**不覆盖**从机的决定。新增目标只需改从机的
路由表，主机无需改配置或重启。

### 5.3 事务配对：载荷内嵌事务号

**问题**：`ds10_driver` 组帧只用 `station_id / function_code / data`，消息里的 `tx_seq`
**不会上无线**。请求与回复的配对因此必须靠 `data` 内自带的序号，否则从机任何一帧上行都会
被主机误当作「回复」。

**方案**：在 `data` 开头嵌入事务头。选 0xF1 开头 + 大端布局，与既有 pyserial 工具**线上
格式一致**，保证 C++ 节点与 Python 脚本互通（已双向验证，字节级一致）。

### 5.4 请求/回复用不同魔数（防静默误路由的关键设计）

```
请求  F1 F1 <txn_hi> <txn_lo> <payload...>          (4 B 头)
回复  F1 F2 <txn_hi> <txn_lo> <dst> <payload...>    (5 B 头)
```

回复**必须**用不同的第二魔数字节（F1 **F2**）。这是必要的、不是美观问题：请求与回复的长度
是重叠的，单靠长度无法区分。若两者共用 F1 F1，一个 4 B 头的旧格式回复，其**载荷首字节会被
误读成 `dst`**——而可见 ASCII（32–126）**全部落在合法站号范围（1–247）内**：

| 旧格式回复载荷 | 会被误转发到 |
|---|---|
| `"Hello"` | 站号 72 |
| `"temp=25"` | 站号 116 |

站号「合法」，所以合法性校验拦不住——数据会被**静默投递到错误的从机**，比直接丢弃更糟。
用不同魔数让格式自描述后，旧格式回复被识别为格式不符、计入 `bad_dst` 并告警。此设计有
专门的单元测试（`RequestFormatNeverYieldsDst`）守护，并已在真实电台上复现验证（假冒旧格式
从机的回复被拒绝、目标从机收到 0 字节）。

### 5.5 从机侧路由表

从机（responder 角色）用 `route_map` 参数按载荷内容选 `dst`：

- 格式 `"关键字:站号,关键字:站号"`，如 `"temp:2,humid:3"`；关键字按 **UTF-8 字节匹配**，
  中文可直接用（`"温度:2,湿度:3"`）。
- **首个命中者胜**（顺序有意义，更具体的关键字放前面）。
- `default_dst` 是无命中时的回落，`0` 表示回复但不转发（安全默认）。
- 格式错误或站号越界在**启动时抛错退出**，不会静默不路由。

### 5.6 主机侧状态机与可靠性

- **单事务串行**：一次一个未决事务，单个 pending 事务号即可，无需事务表。
- **超时用一次性定时器**（非阻塞）：`MultiThreadedExecutor` 下不占死回调线程；默认
  `timeout_ms=1500`（按实测最坏 764 ms 留 ~2× 余量）。
- **重试**：`max_retries=2`。首帧丢失是常态（无线本征丢帧 + 从机侧就绪状态主机观测不到），
  故重试是协议的一部分。
- **去重与站号过滤**：只有来源站号匹配且事务号匹配才转发；重复/过期/异站帧一律**计数但
  只在 DEBUG 级打印**（无线重传/迟到是正常现象，用 INFO 会刷屏淹没真失败），累计到
  `~/stats` 的 `ignored`，绝不静默丢弃。
- **转发不带事务头**：`txn`/`dst` 是主机↔从机1 的记账，对目标从机无意义，只转发业务载荷。

`~/stats` 计数：`sent ok failed retried timeouts forwarded no_forward bad_dst oversized
ignored`——`no_forward`（从机主动要求不转发，正常）与 `bad_dst`（格式/站号异常）分开计数。

### 5.7 实测：内容驱动路由 ✅

真实电台，同一主机中继，`route_map="温度:2,湿度:3"`，四条载荷：

| 载荷 | 从机1 决定 | 主机动作 |
|------|-----------|---------|
| `温度=25.3` | dst=2 | 转发给从机2 |
| `湿度=60` | dst=3 | 转发给从机3 |
| `气压=1013` | dst=0 | 不转发 |
| `温度=30.1` | dst=2 | 转发给从机2 |

计数完全对账：`sent=4 ok=4 forwarded=3 no_forward=1 bad_dst=0 ignored=0`。订阅 `/slave2/rx`
独立确认数据从从机2 的物理串口出来，且**不含事务头**（纯业务载荷）。

### 5.8 实测：端到端转发耗时 ✅

固定场景（请求 60 B `上海赛索德智能科技有限公司位于上海市虹口`，回复 66 B
`好的，已收到贵公司准确地址上海虹口区四川北路`，转发给从机2），20 次：

| 阶段 | 平均耗时 |
|------|---------|
| [1] 下行 主机 → 从机1 | ~22.5 ms |
| [2] 从机1 处理（识别 + 组回复） | ~0.35 ms |
| [3] 上行 从机1 → 主机 | ~21.7 ms |
| [4] 主机处理（读 dst + 转发） | ~0.3 ms |
| [5] 下行 主机 → 从机2（转发） | ~22.2 ms |
| **总耗时（从机2 收到）** | **67.0 ms**（p50 66.6，min 64.7，max 71.2） |

**20/20 全成功、0 重试，分布极紧（波动 6.5 ms）。**

**关键结论：**

1. **总耗时 ≈ 3 × 单跳无线延迟**。三段无线各 ~22 ms（此 60/66 B 小载荷下上下行对称，与
   §1.4 大载荷才现的不对称不冲突），从机1/主机处理合计 < 1 ms。
2. **中继软件开销可忽略**（占比 < 1.5%）。降低延迟的唯一杠杆是无线那一跳（由 DS10/SLE
   档位决定），三跳设计天然是单程的 3 倍，这是拓扑决定的下限。
3. 单跳延迟随载荷增长（见 §1.3），故转发大载荷会显著变慢。

### 5.9 部署约束

- **回复载荷 ≤ ~1000 B**：转发依赖上行（从机1→主机），受 §1.4 的 ~1100 B 上行天花板约束。
  回复比请求还多 1 B（`dst`）。请求载荷同样建议 ≤ ~1000 B。
- **不能与自动栈同跑**：交互/耗时测试须只起驱动（`start_ds10.sh`），自动应答器/中继在跑
  会与之抢角色造成重复应答；脚本会检测并告警。

### 5.10 小结

主从转发通信的技术路线 = **载荷内嵌事务头（配对）+ 请求/回复异魔数（防误路由）+ 从机侧
路由表（内容驱动、路由权在从机）+ 主机侧非阻塞状态机（超时/重试/去重）**。实测内容驱动
路由正确、端到端 ~67 ms、软件开销可忽略。

## 第六部分　结论与部署建议

### 6.1 能力结论

| 能力 | 实测状态 |
|------|----------|
| 1 主多从双向透传（Modbus 站号路由） | ✅ 通过 |
| 主从双向并发（下行 + 上行同时） | ✅ 实用负载内零冲突 |
| 多从并发上行、按站号区分来源 | ✅ 帧依次调度、~100% 到达 |
| 主从三跳转发、从机内容驱动路由 | ✅ 通过，端到端 ~67 ms |
| 透传保真（数据/CRC 不变） | ✅ 通过 |

### 6.2 可靠工作区（部署须遵守）

1. **载荷分向限制**：下行 ≤ ~4095 B、上行 ≤ ~1000 B；转发场景按上行算，回复 ≤ ~1000 B。
   大数据应拆成多个小帧、应用层用 `tx_seq` 重组。
2. **发送节奏**：主机连续下行帧间隔 ≥ 5 ms（建议 10 ms）；一般发送间隔 ≥ 单帧串口传输
   时间 × 3~5，避免超发坍缩。
3. **延迟预期**：小帧（≤32 B）单向 ~14 ms；三跳转发（~60 B）~67 ms；大帧延迟高且不可靠。
4. **可靠性**：无线非 100% 可靠，严格不丢由应用层 `tx_seq`/`rx_seq` 对账重传；转发链路
   已内置超时重试。
5. **设备配置**：投入使用前每台 DS10 须用官方小程序配好角色/通道/站号并拨到 RUN（见 §2.3）；
   两端串口参数必须一致。

### 6.3 待现场复测项 🔄

以上实测均基于**近距离桌面（<2 m）环境**。真实部署距离（障碍/多跳）下需复测：
- `frame_timeout_ms` 定界阈值（帧内静默随距离增大）；
- 延迟与丢包率、上行 ~1100 B 天花板（疑与 SLE 档位相关，换配置需复测）；
- 更高负载 / 多上行从机同时争用下的双向冲突边界。
