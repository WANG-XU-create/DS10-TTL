# [ready-for-agent] DS10 一主多从配置脚本

## 问题陈述

用户在机器人本体上要用 DS10 星闪 DTU 搭一套**控制指令无线网**:一台主机向任意从机下发动作控制指令(不是传感器数据)。现在手上有 3 台 DS10(1 主 + 2 从),处于 1 主 1 从的实验阶段。

要让这套网络工作,每台 DS10 都必须先被正确配置到位——主机配成 Modbus 路由模式并绑定从机的 SN,从机配成从机角色并对齐无线与串口参数。DS10 的 AT 配置是一个有状态的多步流程(进 AT → 建草稿 → 一串设置 → 保存重启),任何一步填错、或主从无线档位不一致,链路就建不起来,而且用户很难判断到底是哪一步出了问题、到底配对上没有。

目前 `DS10_Modbus/` 下只有两个透传测试脚本(`ds10_serial_test.py` 串口收发、`ds10_link_test.py` 双口链路验证),缺的正是"把一台 DS10 一条命令配到位、并确认配对成功"这一环。

## 解决方案

提供一个 **Python + pyserial 单文件命令行配置脚本**,与现有两个测试脚本并列、零新依赖、风格一致。用户为每台设备运行一次:

- 配主机:指定角色 master、RUN 串口参数、无线档位,以及要绑定的通道 + 从机 SN(+ 可选 Modbus 从站地址)。脚本按正确顺序下发全部 AT 命令,建草稿、逐项设置、保存重启。
- 配从机:指定角色 slave、RUN 串口参数、无线档位。从机不涉及通道路由。

脚本对每一步打印发出的 AT 命令与设备响应;遇到 `+DS10ERR` 立即停止并报出错误码与原因,让用户一眼看出卡在哪一步。保存重启后,脚本自动重连设备并读回角色、工作模式、通道绑定与链路状态,与期望值比对,最终打印"✅ 配置已生效"或列出所有不符项。

配对成功后,用户即可用现有 `ds10_link_test.py` / `ds10_serial_test.py` 做透传验证。

## 用户故事

1. 作为机器人集成人员,我希望用一条命令就能把一台 DS10 配成主机,这样我每次就不必手工敲那一长串多步 AT 命令。
2. 作为机器人集成人员,我希望用一条命令就能把一台 DS10 配成从机,这样链路两端的配置能保持一致。
3. 作为机器人集成人员,我希望主机被置为 Modbus 路由模式,这样我只要改帧里的 Modbus 从站地址就能寻址到任意从机,而无需在运行时重新进入配置态。
4. 作为机器人集成人员,我希望在主机上把某个从机的 SN 绑定到某个通道(并可选带上 Modbus 地址),这样主机就能把发往该地址的 Modbus 请求路由到正确的从机。
5. 作为机器人集成人员,我希望通过参数传入从机 SN,这样我就能填入从从机上读到的值(主机无法自动发现未绑定的从机)。
6. 作为机器人集成人员,我希望主机和从机被设成相同的无线 SLE 预设,这样它们才能真正建立链路。
7. 作为机器人集成人员,我希望两台 DS10 的 RUN UART 都被设为 115200 8N1,这样无线管道能与我 Jetson 侧的 Modbus 主机软件、以及执行器的 Modbus 口端到端一致。
8. 作为机器人集成人员,我希望脚本运行时打印出每一条 AT 命令及其响应,这样我能准确跟踪到底往设备发了什么。
9. 作为机器人集成人员,我希望脚本在任何 `+DS10ERR` 时停止并报出错误码与原因,这样我能立刻知道是哪一步失败、为什么失败。
10. 作为机器人集成人员,我希望脚本在保存触发的重启后重连并读回配置,这样我一次运行就能得到"成功了 / 哪里不对"的确定答案。
11. 作为机器人集成人员,我希望读回内容包含无线链路状态,这样我能确认主机确实与所绑定的从机建立了链路(这也正好覆盖"匹配的 SLE 预设是否足以建链"这个文档未明确的问题)。
12. 作为机器人集成人员,我希望能读取一台 DS10 自身的 SN 和设备信息,这样我就能拿到从机 SN 去填进主机的绑定参数。
13. 作为机器人集成人员,我希望脚本使用稳定的 `by-id` 串口路径,这样 DS10 网络和独立的 Temperature_Modbus 传感器总线的 `ttyUSB*` 编号绝不会在开机时被互换。
14. 作为机器人集成人员,我希望脚本失败时给出清晰的非零退出码,这样我能从部署自动化里调用它并检测出问题。
15. 作为机器人集成人员,我希望能安全地重复运行同一条命令,这样重新配置一台设备是可重复且幂等的。

## 实现决策

- **新增独立模块**:一个 Python + pyserial 单文件脚本,与 `ds10_serial_test.py`、`ds10_link_test.py` 并列放在 `DS10_Modbus/` 根目录。零新依赖;沿用现有脚本的结构(argparse 的 `parse_args`、返回退出码的 `main()`、中文帮助文本与提示信息、`dump()` 风格的收发帧打印)。
- **一个脚本、两种角色**:`--role master` 与 `--role slave` 复用同一套 AT 会话机制,只是命令集不同。角色决定是否接受通道/绑定相关参数。
- **主机进入 Modbus 模式**(`CFG_WORK=1`)。正是这个决策让主机能在运行时仅凭帧里的 Modbus 从站地址就寻址到任意从机——无需重进配置态来切换目标。已对照 AT 文档确认:RUN 态是纯串口透传,没有任何运行态发送/寻址命令;目标选择由配置态的路由规则静态决定。
- **主机侧的通道绑定**:`--bind <channel>,<slaveSN>[,<addr>]` 映射到 DS10 的 `CFG_CH` 属性序列——启用通道、把属性 1 设为从机 SN、把属性 2 设为 Modbus 地址/路由。本阶段一台从机 DS10 = 一个 Modbus 从站地址;地址参数为后续扩展成地址段留出空间,而无需改动接口。
- **从机 SN 是输入,绝不自动发现**:AT 命令集没有任何办法让主机枚举未绑定的从机。SN(12 字符、`DS` 开头、通过 Luhn 校验)必须先从从机上读出,再传给主机的 `--bind`。脚本在发送前校验 SN 格式。
- **从机不配置任何路由**:从机侧的配置只有角色 + RUN UART + 无线预设(+ 可选功率/STATUS)。通道绑定纯属主机的事。
- **RUN UART 固定为 115200 8N1**,贯穿主机 DS10、从机 DS10 与执行器的 Modbus 口。这是 DS10 控制网自己的波特率,与 Temperature_Modbus 传感器总线(在物理上独立的串口上跑 9600)无关。
- **无线 SLE 预设:Polar 码 + 均衡档(frameType=1, tier=1)**,主从两端配成完全相同。脚本总是显式下发 SLE 预设,而不依赖 `CFG_NEW` 草稿的默认值,因为文档并未说明该默认档位是什么。
- **文档未覆盖事实的处理方式(不做静默假设)**:AT 文档没有说明 (a) 主从 SLE 预设是否必须一致才能建链,也没有说明 (b) `CFG_NEW` 的默认 frame/tier。脚本对这两点的应对是同一个:在两端都显式设置无线预设,然后在读回阶段检查链路状态以确认链路确实建立——而不是去信任某个默认值或某条假定的规则。
- **有状态的 AT 会话流程**:进入 AT(`+++` 然后 `AT`)→ `CFG_NEW`(RAM 草稿)→ 按角色逐项设置命令 → `CFG_SAVE`(持久化 + 重启)。每一步都读取并回显设备响应;`+DS10ERR` 响应会中止序列并报出错误码/原因。
- **保存会触发重启**:`CFG_SAVE` 之后脚本关闭串口,在带重试的重连窗口里等待,重新打开、重进 AT,读回状态(角色、工作模式)、通道绑定(主机)与链路状态,并与期望值比对。
- **稳定的串口路径**:脚本接受并在文档中要求使用 `/dev/serial/by-id/...` 路径(与 Temperature_Modbus 相同的约定),使两条独立串口总线的 `ttyUSB*` 编号无法在开机时互换。这让 DS10 控制网与传感器总线保持完全隔离(独立端口、独立路径;后续用 ROS 2 封装时再加独立命名空间)。
- **退出码**:验证成功为 `0`;打开/连接失败、序列中途 `+DS10ERR`、读回不符各用不同的非零码——这样部署自动化能区分不同结果。

## 测试决策

- **这里怎样才算好测试**:只断言在串口边界上可观测的外部行为——给定一条 CLI 调用后脚本发出的 AT 帧的顺序与内容,以及脚本对收到的返回帧(成功、`+DS10ERR`、重启/重连、读回符合/不符)如何反应。不测试内部辅助函数或私有结构。
- **单一 seam,处于最高层**:让脚本的 CLI 端到端地对着**一个用 PTY pair 讲 AT 的假 DS10** 运行。串口是脚本唯一的边界,所以它是唯一的 seam——不对内部的"AT 会话"对象做更低层的 mock。假 DS10 应答 AT 序列,能被指示在指定步骤回 `+DS10ERR`,模拟 `CFG_SAVE` 重启(先断开连接再重新接受),并用可配置的值应答读回查询(状态、通道绑定、链路)。
- **被测模块**:配置脚本的 CLI,针对 `--role master`(含 `--bind` 以及对通道绑定 + 链路状态的读回验证)和 `--role slave` 两种情况分别验证。
- **先例(prior art)**:`modbus_rtu_bus_driver` 包已有一个基于 PTY 的集成测试,通过伪终端让 libmodbus 对着一个假从机运行;复用该做法及其来之不易的 PTY 规则(假的一侧持有 PTY 的 master 端,并把对端正在打开/重启期间出现的瞬态 `EIO`/`EAGAIN` 视为非致命,采用轮询而不是退出)。本机已具备 `pytest 6.2.5` 与 `pyserial 3.5`。
- **需覆盖的代表性用例**:主机正常路径(发出正确的 AT 顺序、读回相符、链路建立 → 退出 0);从机正常路径;序列中途 `+DS10ERR` 以正确的退出码中止并报出错误码/原因;读回不符被报告并非零退出;非法从机 SN(前缀错误 / Luhn 校验失败)在发出任何帧之前就被拒绝;模拟重启后在重试窗口内重连成功。

## 范围之外

- **经主机的从机到从机中转。** 固件不原生支持把一台从机的数据转发给另一台;这需要在 Jetson 上做应用层转发,推迟到 ROS 2 集成阶段。本脚本只负责搭起主机→从机下行与从机→主机上行。
- **ROS 2 集成。** 把 DS10 控制网封装为 ROS 2 节点/命名空间(以及真正下发动作命令的 Jetson 侧 Modbus 主机软件)属于后续阶段。本 spec 只覆盖设备配置脚本。
- **端到端透传 / 吞吐测试。** 丢包与延迟验证已由现有的 `ds10_link_test.py` 和 `ds10_serial_test.py` 承担;本脚本的读回确认的是配置与链路建立,而非负载吞吐。
- **Temperature_Modbus。** 完全独立的项目;不做修改。仅在论证串口与命名空间隔离时引用。
- **多从机 / 地址段拓扑。** 接口为每通道的地址段留出了空间,但本阶段目标是一从机 = 一地址。
- **执行器/动作命令格式。** 承载于 Modbus 之上的具体动作命令尚未定义,不属于本脚本。
- **把从机 DS10 接到执行器总线。** 从机在物理上迁移到执行器侧,发生在配置与链路验证之后;实验阶段两台 DS10 都留在 Jetson 上。

## 补充说明

- **脚本所依据的 AT 事实**(来自 `DS10_Modbus/docs/`):RUN 态是纯串口透传,没有发送/寻址类 AT 命令;更改路由目标需要 `CFG_NEW → 改 CFG_CH → CFG_SAVE → 重启`;设备自身的 SN/信息来自设备信息查询(型号、SN、版本、maxSlaves——不含 MAC/角色);角色来自状态查询;主机的逐通道链路查询在链路建立后会把所绑定从机的 SN 报为对端(这是建链后的链路上报,不是发现手段);从机不需要 `CFG_CH`。
- **两处文档空白**(见"实现决策"):主从 SLE 预设是否必须一致才能建链、以及 `CFG_NEW` 的默认 frame/tier,文档都未说明。以显式设置预设 + 读回链路状态来应对,而非做假设。
- **波特率注意**:现有 DS10 测试脚本默认 115200,而 Temperature_Modbus 传感器总线跑 9600。它们是不同的物理总线;此处选 115200 是 DS10 控制网自己的速率,必须与执行器一致,因此若目标执行器只支持其他波特率,该值必须贯穿全部四个点(主机 DS10 的 RUN UART、Jetson 主机软件、从机 DS10 的 RUN UART、执行器)。
- **现有硬件**:3 台 DS10(1 主 + 2 从);实验阶段使用 1 主 + 1 从,当前都在 Jetson 上。
